# 학습 영역과 계속 확장하는 목차

토픽 하나는 10~20분 동안 하나의 원리, 동작, 실패 경계 또는 설계 판단을 다룬다.
현재 총 **132개 토픽 / 44세션**이다. 기존 66개 토픽과 22세션은 유지하고, 66개 토픽과 22세션을 뒤에 추가했다.
실제 목록과 백엔드 출발 질문은 [`topics.yaml`](topics.yaml), 개인별 순서는 [`schedule.yaml`](schedule.yaml)이 기준이다.

## 영역과 단계

| 영역 | 카테고리 | 토픽 수 | 다루는 질문 |
|---|---|---:|---|
| 기본 CS | `arch`, `os`, `net`, `ds`, `db` | 72 | 실행·메모리·네트워크·자료구조·DB가 어떻게 동작하는가? |
| 대규모 아키텍처·시스템 설계 | `design` | 12 | 요구사항과 규모 제약에서 어떤 구조와 경계를 선택할까? |
| 분산 시스템 | `dist` | 9 | 서비스 사이에서 시간·실패·중복·순서를 어떻게 다룰까? |
| 인프라·배포·운영 | `infra` | 9 | 트래픽 변화와 배포·복구 중에도 서비스를 어떻게 운영할까? |
| 관측성·진단 | `observability` | 6 | 로그·덤프·지표·추적에서 원인 가설을 어떻게 검증할까? |
| 성능 엔지니어링 | `perf` | 6 | 처리량과 지연을 어떻게 측정하고 병목을 좁힐까? |
| 실제 코드베이스·프로젝트 문제 | `practice` | 9 | 사용자에게 보이는 증상을 재현하고 수정 효과를 검증할 수 있을까? |
| 심화 분산·데이터·아키텍처 | `advanced` | 9 | 복제·인과관계·재처리·리전·샤드의 어려운 경계를 어떻게 다룰까? |

단계는 학습 영역의 구분이다. 배정 알고리즘은 기존처럼 카테고리 안에서 랜덤 배정하며, 이미 배정된 세션은 바꾸지 않는다.
강제 선행 순서는 목차에 넣지 않고, 실제 학습 때 노트의 `prerequisites`와 `leads_to`로 필요한 연결을 확정한다.
설계부터 심화까지의 목차가 있다고 해당 내용을 이미 학습한 것으로 처리하지 않는다.

기본 CS 준비도는 다섯 기본 카테고리만 계산한다. 기본 CS 70%는 실전 학습을 권장하는 시점이지 후속 목차 작성을 금지하는 기준이 아니다.

## 이번에 추가한 목차

- **기본 CS 보강 6개**: 가상 스레드, 협력적 취소, 스레드 풀 내부 대기, 커넥션 풀 크기, 외부 호출을 포함한 트랜잭션 경계, 키셋 페이지네이션.
- **시스템 설계 12개**: 요구사항·SLO, 데이터 증가와 보관, 서비스 경계, 데이터 소유권, 캐시 갱신 순서, 다중 리전 라우팅, 피드 팬아웃, 채팅 전달 확인, 단축 URL 식별자 공간, 업로드 처리 경계, 주문 상태 전이, 아키텍처 결정 기록.
- **분산 시스템 9개**: 데드라인·취소, 벌크헤드, 서킷 브레이커, 아웃박스, 소비자 멱등성, 이벤트 순서, 사가 보상, 백프레셔, 펜싱 토큰.
- **운영 9개**: 헬스·준비 상태, 요청 드레이닝, 설정·비밀값, 동적 서비스 발견, 증설 지연, 복구 훈련, 스키마 변경, 카나리, 산출물 승격.
- **관측 6개**: 스레드 덤프, 지연 분포, 분산 추적, 로그 상관관계, 사용자 증상 알림, 장애 타임라인.
- **성능 6개**: 리틀의 법칙, 대기열 지연, 부하 모델, CPU 프로파일, 객체 할당·GC, 벤치마크 오차.
- **실전 9개**: 송금 멈춤, 커넥션 풀 고갈, 내보내기 메모리 급증, 옛 가격 재등장, 재시도 폭주, 배포 중 5xx, 페이지 중복·누락, 반복 실패 메시지, 주문 일부 성공.
- **심화 9개**: Raft 커밋, 논리 시계, CRDT 카운터, 리전 쓰기 충돌, CDC 재구축, 워터마크, 온라인 샤드 이동, 과부하 요청 제한, 서비스 신원.

## 실제 프로젝트 문제의 기본 연결과 실험 출발점

다음은 학습할 때 사용할 연결 **후보**다. 현재 노트의 그래프 링크를 대신하지 않는다.
실전 목차는 실제 운영 사고를 조사한 기록이 아니라 재현할 가상 시나리오다.
사용자가 프로젝트를 제공하면 실제 코드·호출 경로·설정·측정 증거를 근거로 해당 시나리오를 구체화한다.

| 실전 토픽 | 기본 CS 선행 후보 (2개 이상) | 재현·관측 출발점 | 후속 후보 |
|---|---|---|---|
| `practice.transfer-hang` | `os.deadlock`, `os.sync-primitive`, `os.thread` | 두 락의 반대 획득 순서와 스레드 덤프의 소유·대기 고리 | `observability.thread-dump`, `dist.deadline-propagation` |
| `practice.connection-pool-exhaustion` | `os.sync-primitive`, `db.transaction` | 작은 풀에서 연결 점유 시간과 대기 요청 수 비교 | `db.connection-pool-sizing`, `dist.bulkhead` |
| `practice.export-memory-spike` | `os.process`, `os.virtual-memory` | 결과 전체 적재와 스트리밍 처리의 메모리 사용량 비교 | `perf.allocation-gc`, `design.upload-pipeline` |
| `practice.stale-cache-price` | `os.race-atomic`, `db.transaction` | 읽기·갱신·캐시 저장의 순서를 통제하고 재등장한 값 추적 | `design.cache-consistency`, `advanced.logical-clock` |
| `practice.retry-storm` | `net.timeout-retry`, `os.thread` | 의존 서비스 실패 전후의 요청 도착률·재시도 횟수 비교 | `dist.circuit-breaker`, `advanced.load-shedding` |
| `practice.deploy-5xx` | `os.signal-ipc`, `net.load-balancer` | 긴 요청 중 인스턴스 교체와 라우팅·종료 타임라인 추적 | `infra.rolling-drain`, `infra.canary-rollout` |
| `practice.pagination-duplicates` | `db.index-design`, `db.isolation` | 페이지 사이에 삽입을 재현하고 정렬 키·조회 시점 비교 | `db.keyset-pagination`, `design.feed-fanout` |
| `practice.queue-poison-message` | `net.timeout-retry`, `ds.stack-queue` | 계속 실패하는 메시지 하나와 뒤의 정상 메시지 대기 측정 | `dist.backpressure`, `dist.idempotent-consumer` |
| `practice.partial-order-success` | `db.transaction`, `net.http-semantics` | DB 커밋과 후속 호출 사이에 실패를 주입하고 상태·이벤트 대조 | `dist.transactional-outbox`, `dist.saga-compensation` |

## 다음 레벨로 연결하는 방법

시스템 전체를 한 번에 설계하지 않는다. 하나의 작은 경계를 이해한 뒤 그 결과에서 다음 질문을 만든다.

| 학습 흐름 예시 | 다음에 확인할 질문 |
|---|---|
| 스레드·락 → 데드락 → 덤프 → 송금 장애 → 취소·격리 | 요청이 끝난 뒤 서버 자원을 실제로 정리하는 경계는 어디인가? |
| 트랜잭션 → 아웃박스 → 중복 소비 → 주문 일부 성공 → CDC 재구축 | 실패 뒤 재처리해도 어떤 상태와 외부 효과를 유지해야 하는가? |
| 복제·샤딩 → 서비스 소유권 → 리전 라우팅 → 리전 쓰기 충돌 → 온라인 이동 | 데이터 담당자가 바뀌는 동안 읽기와 쓰기를 어떻게 연결할까? |
| 큐·스레드 → 리틀의 법칙 → 부하 모델 → 백프레셔 → 과부하 요청 제한 | 시스템이 감당하지 못하는 요청을 언제 어디에서 제한할까? |

이 표는 강제 수강 순서가 아니다. 실제 이해한 내용과 코드에서 확인한 경계를 노트로 연결하기 위한 예시다.

## 끝을 두지 않는 확장 절차

1. 매 학습 세션에서 범위 밖의 유용한 질문을 `suggest`에 하나 이상 남긴다. 큰 질문은 10~20분 크기로 쪼갠다.
2. `expand`에서 제안, 그래프의 빈 곳, 사용자가 요청한 새 영역과 프로젝트의 실패 경계를 모은다. 이미 있는 내용은 새 이름으로 중복 추가하지 않는다.
3. 하나의 개념마다 다음 단계의 구현 실험, 관측 증거, 설계 트레이드오프를 찾는다. 다른 영역이면 새 카테고리를 만들 수 있다.
4. 카테고리별 새 토픽을 팀원 수의 배수로 추가하고 `npm run assign`으로 기존 배정 뒤에 붙인다.
5. 목차·권장 연결·카테고리 색·README 수치를 갱신한 뒤 검증하고 별도의 `curriculum:` PR로 공유한다.
6. 배정이 끝나거나 제안이 쌓이면 같은 절차를 다시 반복한다. `advanced`는 마지막 카테고리나 종료 조건이 아니다.

학습 중에는 현재 토픽에 집중하고 새 목차는 따로 확장한다. 더 많은 목록을 만들었다는 이유로 한 세션을 길게 늘리지 않는다.
