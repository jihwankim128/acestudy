## 한 줄 요약

**락을 기다리는 것 자체는 데드락이 아니다. 서로 필요한 락을 쥔 채 기다리는 고리가 생겨 진행하지 못하는 것이 데드락이다.**
락 획득 순서 통일은 순환 대기를 끊고, 획득 실패 시 보유 락을 해제한 뒤 재시도하는 방식은 점유 대기를 끊는다.

## 핵심 개념

### 1. 일반적인 대기와 데드락

학습자가 처음 설명한 장면은 다음과 같다.

> A가 1번 자원, B가 2번 자원을 먼저 잡은 뒤 다음 작업에서 서로의 자원이 필요해 둘 다 기다린다.

여기서 정확한 표현은 **첫 번째 락을 쥔 채 두 번째 락을 기다린다**이다. 자원에 접근했다는 사실만으로는 부족하다.

```text
A: 1번 락 보유 → 2번 락 대기
B: 2번 락 보유 → 1번 락 대기
```

타임아웃이나 외부 복구가 없는 이 두 락의 예시에서는 서로가 락을 풀어야 진행할 수 있지만, 둘 다 대기 중이라 풀 수 없다.
반대로 A가 작업 후 락을 풀 수 있고 B만 기다리는 경우는 일반적인 락 대기다.

### 2. 데드락의 네 필요조건

| 조건 | 이번 예시에서의 의미 |
|---|---|
| 상호 배제 | 계좌 락을 한 번에 하나의 스레드만 보유한다 |
| 점유 대기 | 첫 계좌 락을 쥔 채 두 번째 락을 기다린다 |
| 비선점 | 다른 스레드가 보유자의 락을 강제로 빼앗지 못한다 |
| 순환 대기 | A는 B를, B는 A를 기다린다 |

이 자원 모델에서 데드락이 발생하려면 네 조건이 모두 필요하다. 하나라도 깨뜨리면 예방할 수 있다.
이 조건을 허용하는 설계라고 해서 매 실행에서 반드시 데드락이 생기는 것은 아니다. 실제 실행 순서가 중요하다.

### 3. 송금 방향과 락 획득 순서를 분리한다

처음에는 "작은 번호"가 무엇인지 확인했다. 여기서는 **계좌의 고유 번호**다.

```text
A: 1번 → 2번 송금 / 락은 1번 → 2번
B: 2번 → 1번 송금 / 락은 1번 → 2번
```

A가 1번을 먼저 잡으면 B는 **아무 락도 쥐지 않은 채** 1번에서 기다린다.
따라서 A는 2번을 잡아 작업을 끝낼 수 있고, A가 풀면 B도 진행한다.

학습자의 표현: **"단방향으로 흐르면서 순환 대기를 깨뜨려준다."**
세 개 이상의 락에도 같은 논리가 적용된다. 엄격한 순서를 따라 증가만 한다면 원래 락으로 돌아오는 고리를 만들 수 없다.
모든 획득 경로와 내부 호출이 같은 순서를 지켜야 한다. 동일 계좌를 두 번 잠그는 입력은 별도로 처리하고, 계좌 ID마다 동일한 락 객체를 사용해야 한다.

### 4. 실패 시 해제는 데드락을 막지만 완료까지 보장하지는 않는다

두 번째 락은 블로킹 획득 대신 즉시 성공·실패를 반환하는 try-lock으로 시도한다.
실패하면 **첫 락부터 풀고** 대기·재시도한다. 첫 락을 쥔 채 잠드는 구현과 구분해야 한다.

```text
A는 1번 획득 / B는 2번 획득
둘 다 두 번째 락 획득 실패
둘 다 첫 락 해제
같은 타이밍에 재시도 → 계속 같은 충돌
```

학습자는 실행 순서를 적어 보며 **"데드락이 아니라 무한 재시도가 될 수 있다"**고 스스로 수정했다.
서로 양보하고 재시도하지만 작업이 진전되지 않는 이 패턴은 라이브락이다.
랜덤 대기는 반복 충돌 가능성을 줄일 수 있지만 성공의 절대 보장은 아니다. 시간 예산과 재시도 상한도 필요하다. 이 부분은 별도 학습 후보로 남긴다.

## 백엔드에서는

### 클라이언트 타임아웃은 서버의 락 해제가 아니다

```text
0초: 서버 A와 B가 서로의 락을 기다림
3초: 클라이언트가 응답 기다리기를 포기함
이후: 별도 서버 취소·정리가 없다면 A와 B는 여전히 대기
```

"최대 3초 동안만 데드락"이라는 이해를 교정했다. 3초는 클라이언트의 대기 제한일 뿐이다.
서버 작업이 계속 실행되는 것도 아니다. 이 예시의 스레드는 **멈춘 채 락을 보유**하고 있다.
같은 계좌로 재시도하는 새 요청도 기존 락 뒤에서 대기할 수 있다. 매 재시도가 새 데드락을 만든다는 뜻은 아니다.

스레드 풀을 200개에서 400개로 늘려도 이미 생긴 고리는 없어지지 않는다.
이 두 계좌를 모두 잠가야 하는 송금의 처리량은 0이고, 더 많은 요청이 기다릴 공간만 생긴다.
스레드 수가 두 배라고 데드락 발생 확률도 정확히 두 배가 되는 것은 아니다.

### 스레드 덤프: "지금 각 스레드가 어디에 있는가"의 스냅샷

일반 요청 로그는 코드가 로그를 쓰도록 구현한 지점의 이벤트다.
**스레드 덤프**는 실행 중인 JVM에 요청해 각 스레드의 이름, 상태, 호출 스택, 락 정보를 한 시점에 출력한 진단 기록이다.
예외가 발생해야만 얻을 수 있는 것이 아니고, 일반 로그에 자동으로 항상 남는 것도 아니다.

```bash
# PID는 진단하려는 Java 프로세스의 숫자 ID로 바꾼다.
jcmd <PID> Thread.print -l > thread-dump.txt
```

`Thread.print`는 스택을 출력하고 `-l`은 java.util.concurrent 락 정보도 포함한다.
대상 JVM과 같은 머신·사용자 권한에서 실행한다. JVM 구현과 락 종류에 따라 표현은 달라질 수 있다.

이번 세션의 macOS / Corretto OpenJDK 21 플랫폼 스레드 실험에서 실제 출력한 부분이다.
아래 주소는 그 실행의 객체 식별값이며, 계좌 번호 자체가 아니다.

```text
Found one Java-level deadlock:
=============================
"A":
  waiting to lock monitor 0x00000001507d27b0 (object 0x000000069754e0c8, a java.lang.Object),
  which is held by "B"

"B":
  waiting to lock monitor 0x0000000131d04390 (object 0x000000069754e0b8, a java.lang.Object),
  which is held by "A"
```

이 두 개의 `which is held by`를 읽으면 **A → B → A**다.
스택에서는 `waiting to lock <주소>`가 요청 중인 락, `locked <주소>`가 이미 보유한 락이다.
같은 객체 주소를 대조하면 대기 락의 소유자를 따라갈 수 있다.

**BLOCKED 상태가 많다는 사실이나 낮은 CPU 사용률만으로 데드락을 확정하지 않는다.**
보유와 대기를 연결한 순환, 그리고 실제 스택을 증거로 확인한다.
JVM은 지원하는 모니터·소유 가능한 동기화 객체의 데드락을 보고할 수 있지만, 모든 종류의 응답 대기나 분산 시스템의 고리를 자동으로 찾아주는 것은 아니다.

## 실험

이 노트와 같은 폴더의 `os.deadlock.demo.java`를 별도 터미널에서 실행한다.

```bash
java notes/os/os.deadlock.demo.java deadlock
java notes/os/os.deadlock.demo.java ordered
```

첫 모드는 두 스레드가 각자 첫 락을 잡을 때까지 기다리게 해, 반대 순서의 데드락을 확실하게 재현한다.
두 번째 모드는 둘 다 1번 → 2번 순서다. 덤프를 얻으려면 첫 터미널에서 다음 명령을 실행한다.

```bash
java notes/os/os.deadlock.demo.java deadlock dump
# 출력된 PID를 사용해 30초 이내에 다른 터미널에서 실행:
jcmd <PID> Thread.print -l
```

실제 결과: 반대 순서는 `Deadlocked threads: 2`, 동일 순서는 `Both transfers completed: true`와 `Deadlocked threads: 0`이었다.
실험은 의도적으로 데드락을 만든다. 스레드를 daemon으로 만들어 진단 후 프로세스가 종료되도록 했다. 서버의 복구 기법을 구현한 예제가 아니다.
`ThreadMXBean.findDeadlockedThreads()` 검사는 여기서 사용한 플랫폼 스레드에 적용한다. 가상 스레드 검사는 지원하지 않는다.

## 확인 질문

- 데드락과 라이브락의 차이는 자신의 말로 설명했다.
- 순서 통일이 순환 대기, 해제 후 재시도가 점유 대기를 끊는다는 점을 직접 연결했다.
- 덤프 진단은 처음 접했다. 자원 번호로 `A → 2`, `B → 1`을 적은 뒤, 소유 스레드를 따라 `A → B`, `B → A`를 연결했다.
- "스레드 덤프가 무엇이며 그 고리가 실제 로그에 보이는가"라는 후속 질문에 실제 `jcmd` 출력으로 보완했다. 덤프 읽기를 처음부터 알고 있었다고 기록하지 않는다.
