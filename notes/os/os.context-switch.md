## 한 줄 요약

**컨텍스트 스위칭은 실행 상태를 보존하고 CPU에서 실행할 스레드를 바꾸는 작업이다. 교대에는 비용이 들지만, I/O 대기로 비는 CPU를 다른 요청의 계산으로 채울 수도 있다.**

## 핵심 개념

### 1. 요청을 맡기는 주체와 CPU에서 실행할 스레드를 고르는 주체

학습의 출발점은 “CPU만 쓰면 코어 수가 처리량을 결정할 것 같은데, CPU가 스레드에게 일을 부여하는 것과 어떤 관련이 있나?”였다.

일반적인 OS 스레드 기반 서버의 작업 스레드 모델에서는 다음 역할을 구분한다.

```text
서버 프로그램: 요청을 작업 스레드에서 처리하게 한다
OS 스케줄러:   실행 가능한 스레드 중 CPU에서 실행할 대상을 선택한다
CPU:           선택된 스레드의 명령어를 실행한다
```

이 노트의 계산에서는 코어 하나에 스레드 하나를 실행한다고 단순화한다. SMT, 가상 스레드, 컨테이너 CPU 제한 등은 모델에 포함하지 않는다.

코어 2개가 이미 계산으로 꽉 찼다면 스레드를 2개에서 20개로 늘려도 동시에 계산하는 능력은 늘지 않는다. 실행 중인 2개 외에 준비된 스레드는 자기 차례를 기다린다. 스레드 수와 교대 횟수가 정확히 비례하는 것은 아니다.

### 2. 어디까지 실행했는지와 무엇을 계산 중이었는지

학습자는 먼저 “어디까지 작업했는지”, 이어서 “개별 스택”을 보존해야 한다고 답했다. 여기에 계산 중간값이 담긴 레지스터를 더하면 된다.

| 보존하는 것 | 이어서 실행할 때 필요한 이유 |
|---|---|
| PC 등 복귀할 명령어 위치 | 다음에 어디서 실행할지 알아야 한다 |
| SP 등 스택 위치 | 자기 호출 기록과 지역 변수에 다시 접근해야 한다 |
| 그 밖의 필요한 레지스터 값 | CPU에 있던 계산 중간값을 이어 써야 한다 |
| 메모리에 남은 스택 내용 | 중단 전의 호출 기록과 지역 변수를 유지해야 한다 |

```text
A 실행 → A의 실행 상태 보존 → B의 실행 상태 복원 → B 실행
```

**스택은 메모리에 남는다. 교대할 때 스택 전체를 복사하는 것이 아니다.** A→B 교대 때 20개 스레드 모두의 상태를 다시 저장하지도 않는다.

위 순서는 개념도다. 실제 저장은 하드웨어의 인터럽트·트랩 처리와 커널 코드에 나뉠 수 있고, 저장할 레지스터와 위치는 CPU 아키텍처·OS 구현에 따라 달라진다. 같은 프로세스의 스레드는 주소 공간을 공유하므로 힙 전체를 복사할 필요도 없다.

### 3. 보관 공간의 비용과 교대에 쓰는 CPU 시간

- 메모리 비용: 스레드마다 스택과 실행 상태를 보관할 공간이 필요하다.
- 직접적인 CPU 비용: 스케줄러 실행과 상태 저장·복원에 CPU 시간을 쓴다.
- 간접적인 비용: 다른 실행 흐름의 데이터가 기존 데이터를 캐시에서 밀어내면, 재개 후 다시 가져오는 비용이 생길 수 있다.

교대마다 CPU 캐시 전체가 초기화되는 것은 아니다. 비용을 고정된 몇 µs라고 가정하지 말고 하드웨어, 작업 집합, 스케줄링과 부하 조건에서 측정한다.

### 4. CPU 계산만 하는 경우와 I/O를 기다리는 경우

**CPU 계산만 하는 요청의 예시**

코어 2개, 요청당 CPU 계산 10ms라면 부가 비용이 없는 이상적인 상한은 `2 × 1,000ms ÷ 10ms = 200개/초`다.

전체 CPU 시간의 10%를 교대 등 부가 작업에 쓴다고 **가정**하면 다음과 같다. 실제로 교대 비용을 측정해 얻은 비율은 아니다.

```text
요청 계산에 쓸 시간 = 2 × 1,000ms × 0.9 = 1,800ms
처리량              = 1,800ms ÷ 10ms = 180개/초
```

학습자는 처음 `10ms + 1ms = 11ms`로 계산했다. 전체 시간의 10%가 부가 비용이라면 그 비용을 배분한 요청당 평균 코어 점유 시간은 `10ms ÷ 0.9 ≈ 11.11ms`다. 실행 대기까지 포함한 실제 요청 응답 시간과는 구분한다. `11ms`는 계산 시간 10ms의 10%를 더한 값이다.

**블로킹 I/O가 있는 요청의 예시**

학습자는 처음에는 I/O 대기 중에도 교대 비용 때문에 처리량이 떨어진다고 생각했다. A가 DB를 기다릴 때는 A의 다음 계산을 진행할 수 없다는 장면을 확인한 뒤, 아래 두 경우를 직접 계산했다.

코어 1개, 요청당 CPU 계산 10ms + DB 대기 90ms, 충분한 요청과 DB 용량, 교대 비용 무시를 가정한다.

| 작업 스레드 수 | 정상 상태에서 CPU가 계산하는 비율 | 이상적인 처리량 |
|---|---|---|
| 1개 | 10% — 계산 10ms 뒤 다른 준비된 작업이 없으면 90ms 쉰다 | 10개/초 |
| 10개 | 100% — 한 스레드의 대기 중 다른 9개가 각각 10ms 계산한다 | 100개/초 |

각 요청은 여전히 DB를 90ms 기다린다. 늘어나는 것은 동시에 진행 중인 요청 수와 완료 처리량이다. 실제 서버에서는 DB·커넥션 풀의 용량과 교대 비용 등에 따라 결과가 달라진다.

## 백엔드에서는

**증상: CPU 100%인 서버에서 작업 스레드를 20개에서 200개로 늘렸더니 처리량은 그대로이고 응답 시간만 늘었다.**

학습자는 코어 수와 요청 수를 확인한 뒤 스레드를 줄이자고 제안했다. 축소를 실험할 방향은 맞지만, 그 두 숫자만으로 컨텍스트 스위칭이 원인이라고 확정할 수는 없다.

같은 요청 도착률과 작업 구성에서 초당 교대 횟수, 실행 대기 스레드 수, CPU 시간의 구성, 완료 처리량과 p95·p99 응답 시간을 함께 비교한다. 교대가 많다는 사실만으로 손해라고 판정하지 않는다. 스레드를 단계적으로 줄여 처리량은 유지하면서 지연이 줄어드는지 확인한다. 필요하면 CPU 프로파일과 락·DB 병목도 대조한다.

Linux에서 관측하는 예시다. macOS에는 아래 Linux 도구가 기본 제공되지 않으며, 컨테이너에서는 보이는 CPU 수와 실제 CPU 할당량도 구분해야 한다.

```bash
vmstat 1
pidstat -w -t -p 12345 1
```

- `vmstat`의 `r`: 실행 중이거나 실행을 기다리는 작업 수로, 보고 시점의 값이다. `cs`: 시스템 전체의 초당 컨텍스트 스위치다. 첫 보고의 `cs` 등 속도 통계는 부팅 이후 평균이므로 이후 구간을 비교한다.
- `pidstat`의 `cswch/s`: I/O·자원 대기 등으로 CPU를 내놓는 자발적 교대. `nvcswch/s`: 선점으로 인한 비자발적 교대다. `-t`로 스레드별로 보며 시스템 전체 수치와 구분한다.
- 이 횟수는 교대 비용의 시간을 직접 측정한 값이 아니다. 응답 시간·처리량과 함께 해석한다.

커널에 들어갔다가 같은 스레드로 돌아오는 시스템 콜도 있다. **유저/커널 모드 전환과 실행 스레드 교대는 구분한다.** 자세한 경계는 연결 토픽에서 다룬다.

## 실험 — 흐른 시간과 CPU를 쓴 시간 구분하기

macOS에서 Python으로 실행했다. DB 응답 대기를 `sleep`으로 단순화한 모형이며, DB 호출이나 컨텍스트 스위치 비용 자체를 측정한 실험은 아니다.

```bash
python3 - <<'PY'
import time

wall_start = time.perf_counter()
cpu_start = time.process_time()
for _ in range(3):
    work_start = time.process_time()
    while time.process_time() - work_start < 0.010:
        pass
    time.sleep(0.090)
print(f"실제로 흐른 시간: {(time.perf_counter() - wall_start) * 1000:.1f}ms")
print(f"사용한 CPU 시간: {(time.process_time() - cpu_start) * 1000:.1f}ms")
PY
```

세션에서 관측한 값은 **경과 시간 310.5ms, CPU 시간 30.1ms**였다. `process_time()`은 프로세스가 사용한 유저·시스템 CPU 시간을 재며 `sleep` 시간은 포함하지 않는다. 스케줄링과 타이머 지연 때문에 재실행 값은 달라질 수 있다.

확인한 것은 “90ms 동안 요청이 끝나지 않아도 그 90ms를 이 프로세스의 CPU 계산으로 소비한 것은 아니다”라는 점이다. 이 시간에 다른 준비된 스레드를 실행할 수 있다.

## 확인 질문

1. A→B 교대에 보존할 상태와 스택의 처리 방식은? — 학습자는 스택·PC·SP를 답했다. 계산 중간값을 담은 나머지 레지스터도 보존한다는 점을 보완했다.
2. 블로킹 I/O 중 교대가 처리량을 늘릴 수 있는 이유는? — 학습자는 대기 중 다른 스레드가 CPU를 받아 실행할 수 있기 때문이라고 정확히 설명했다.
3. CPU 포화 상태에서 스레드 증설 후 지연만 늘었다면? — 학습자는 코어 수·요청 수를 확인하고 스레드 축소를 제안했다. 초당 교대·실행 대기·완료 처리량·응답 시간을 같은 부하에서 비교해야 한다는 점을 보완했다.
