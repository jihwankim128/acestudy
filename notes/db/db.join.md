## 한 줄 요약

**JOIN 조건은 SQL에 쓰고, 실행 방법은 DB 옵티마이저가 비용을 보고 선택한다. N+1의 SQL 요청 횟수와 DB 내부의 반복 횟수는 다르다.**
이번 실험의 PostgreSQL은 중첩 루프·해시·병합 조인과 정렬을 이미 구현하고 있다. 애플리케이션이 이 알고리즘들을 직접 구현해야 하는 것은 아니다. 지원 방법과 선택 조건은 DB 제품·버전에 따라 다르다.

## 핵심 개념

### 1. SQL 요청 횟수와 내부 작업을 구분한다

주문 목록에 고객 이름을 붙이는 예시다. 주문 100개 조회 후 고객을 각각 조회하면 **1 + 100 = 101번**의 SQL 요청이다. 이것이 이 예시의 N+1이다.

학습자는 처음부터 `JOIN ... LIMIT 100`으로 한 번에 조회하자고 제안했다. 이는 원래 코드의 횟수 계산이 아니라 개선안이었다. 이후 확인 질문에서는 주문 50개에 **51번**, `IN` 일괄 조회에는 **2번**이라고 직접 계산했다.

```sql
-- JOIN: SQL 한 번으로 주문과 고객을 연결한다.
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.id <= 10;
```

이 SQL 하나 안에서 고객 인덱스를 10번 탐색해도 SQL 요청은 한 번이다.
SQL 요청 수는 애플리케이션의 호출 기록으로, 내부 반복은 실행 계획으로 확인한다.
N+1은 반복적인 왕복 비용을 만들지만, JOIN 한 번이라고 내부 작업까지 저렴한 것은 아니다.

### 2. 중첩 루프: 한쪽의 행마다 다른 쪽을 찾는다

학습자는 주문 100개·고객 1만 명에서 리스트를 매번 전부 훑으면 **100만 번 비교**, 해시로 찾으면 **100번 조회**라고 구분했다.

| 방법 | 이 단순한 등가 조인 모델에서의 작업 |
|---|---|
| 매번 고객 전체 스캔 | 주문 N개 × 고객 M명 비교 |
| 고객 인덱스 탐색 | 주문마다 인덱스로 고객 탐색; 대략 N × log M을 출발점으로 생각 |
| 해시 조회 | 해시 테이블을 만드는 작업 + 주문마다 해시 조회 |

중첩 루프가 항상 전체 스캔을 반복하는 것은 아니다. 안쪽 입력에서 인덱스를 사용할 수 있다.
고객 100만 명 중 주문 10개의 고객을 찾는 예시에 학습자는 **기존 인덱스를 10번 탐색**하겠다고 선택했다. 해시 생성에 필요한 읽기와 메모리까지 고려한 판단이다.
실제 시간에는 페이지 접근, 캐시, 필터 후 행 수와 결과 생성 비용도 영향을 준다. 복잡도만으로 실행 시간을 확정하지 않는다.

### 3. 해시 조인: DB 안에서 해시 테이블을 만들고 조회한다

```text
애플리케이션 → JOIN SQL 한 번 → DB 엔진
                                  ├─ Build: 한쪽 입력으로 임시 해시 테이블 생성
                                  └─ Probe: 다른 입력의 조인 키로 조회 → 결과 반환
```

고객 ID가 유일한 예시에서는 `고객 ID → 고객 정보`인 맵처럼 이해할 수 있다. 이름까지 가져오려면 회원 여부만 확인하는 집합을 넘어 고객 정보가 필요하다.
조인 키가 중복되는 일반 입력에서는 같은 키에 여러 행을 보존하고 필요한 결과 조합을 모두 만들어야 한다.

해시를 만드는 쪽이 반드시 고객인 것은 아니다. 필터링된 작은 주문 입력으로 만들고 고객을 스캔하는 계획도 가능하다. **해시 생성에 드는 메모리뿐 아니라 양쪽 입력을 읽는 비용**을 함께 비교한다. 해시 충돌과 출력 행 수 때문에 조회 N번을 정확히 N번의 ID 비교와 동일시하지 않는다.

Hash Join을 실행하려고 SQL에 `GROUP BY`나 `HAVING`을 추가하지 않는다. 이 구문은 집계와 집계 결과 필터링을 표현한다. DB는 같은 JOIN SQL에 해시 조인을 선택할 수 있다.

### 4. 병합 조인: 정렬된 입력을 투 포인터처럼 따라간다

학습자는 고객 쪽 포인터를 옮겨야 한다고 답한 뒤 "투 포인터 전략 아냐? 이걸 실제 DB 조회 시 사용한다고?"라고 연결했다.

```text
주문의 고객 ID: [2, 4, 4, 9]
고객의 ID:      [1, 2, 4, 7, 9]   ← 고객 ID는 유일
```

- 주문 2와 고객 1: 고객 포인터를 앞으로 옮긴다.
- 두 ID가 같으면 결과를 만든다.
- 첫 주문 4를 연결한 뒤 고객 4를 유지하고 다음 주문 4도 연결한다.
- 고객 4의 주문 두 개를 모두 포함해 결과는 총 4행이다.

이 예시에서 주문만 옮기는 이유는 **같은 고객에 연결할 주문이 남아 있고 고객 ID는 유일하기 때문**이다. 조회 대상이라는 이유만으로 항상 한쪽 포인터만 옮기는 규칙은 아니다. 양쪽 키가 모두 중복되면 해당 키 그룹의 결과 조합을 보존하는 처리가 더 필요하다.

### 5. "정렬이 없다"는 DB에 정렬 기능이 없다는 뜻이 아니다

학습자는 처음에 정렬이 없으면 반복 검색 때문에 Nested Loop가 된다고 답했고, 이어서 "이미 다 구현되어 있고 우리는 선택만 하는가? DB에 정렬 알고리즘이 없을 수도 있나?"라고 질문했다.
다음 두 경우를 구분해서 보완했다.

```text
같은 JOIN SQL
    ↓ DB 옵티마이저가 입력 규모·통계·인덱스·예상 비용을 비교
    ├─ Nested Loop + 필요한 고객 인덱스 탐색
    ├─ Hash Join + DB 내부 해시 생성
    └─ Merge Join
           ├─ 정렬 순서를 제공하는 인덱스에서 읽기
           └─ 아직 정렬되지 않았다면 DB가 Sort한 뒤 병합
```

**미정렬 상태는 데이터의 현재 순서에 관한 말이다.** PostgreSQL의 DB 엔진에는 정렬과 병합 조인이 구현되어 있다.
명시적 정렬에는 시간·메모리가 필요하고, 메모리가 부족하면 디스크 작업도 발생할 수 있다. 옵티마이저는 이 비용까지 포함한다.
개발자는 보통 SQL의 결과 조건을 표현하며, 조인 알고리즘을 직접 지정하지 않는다. 인덱스·통계·쿼리 구조를 조정하고 실제 계획과 시간을 확인한다. 실험용 플래너 옵션 조정이 운영 쿼리의 기본 해결법은 아니다.
병합 조인의 입력 순서와 API 결과의 정렬 요구도 구분한다. 결과 순서를 보장하려면 SQL에 명시적인 `ORDER BY`를 쓴다.

### 6. IN 일괄 조회와 커버링 인덱스는 함께 쓸 수 있다

```sql
-- 먼저 주문을 조회하고 고객 ID를 모은다.
SELECT id, customer_id FROM orders WHERE id <= 10;

-- 첫 조회에서 고객 ID 2, 4, 9가 모였다고 가정한 예시다.
-- 실제로는 첫 조회에서 모은 고객 ID를 사용한다.
SELECT id, name FROM customers WHERE id IN (2, 4, 9);
```

이 전략은 SQL 2번 뒤 애플리케이션에서 고객 정보를 각 주문에 붙이는 방식이다. 고객 ID를 중복 제거해 조회해도 원래 주문들은 모두 보존해야 한다.
커버링 인덱스는 **해당 쿼리에 필요한 컬럼들을 인덱스가 담고 있는가**라는 별개의 조건이다. 여기서는 `id`와 `name`이 모두 필요하다.
PostgreSQL에서는 `ON customers(id) INCLUDE(name)`으로 두 값을 담을 수 있지만, 실제 테이블 접근 생략은 행 가시성 상태에도 달려 있다. `IN`을 썼다는 사실만으로 커버링 조회가 되는 것은 아니다.

## 백엔드에서는

목록 API의 SQL 호출 수를 줄이는 판단과, DB가 행을 찾는 방법을 개선하는 판단을 구분한다.
순차 SQL 호출마다 왕복에만 2ms가 걸린다는 가상의 조건에서는 101번 왕복에 202ms가 든다. 실제 서비스에서는 쿼리 실행·결과 전송·커넥션 대기 등도 측정해야 한다.

`Nested Loop`라는 이름만으로 느리다고 판단하지 않는다. 필요한 주문이 적고 고객 인덱스가 적절하면 좋은 계획일 수 있다.
`EXPLAIN`은 예상 계획, `EXPLAIN ANALYZE`는 실제 실행 측정값을 제공한다. 같은 결과·조건·환경에서 실제 시간, 처리 행 수와 버퍼 접근을 비교한다. `cost`는 밀리초가 아니다.

## 실험

Docker가 실행 중인 로컬 환경에서 저장소 루트 기준으로 실행한다.

```bash
bash notes/db/db.join.demo.sh
```

별도 PostgreSQL 컨테이너를 만들고 `db.join.demo.sql`을 실행한 뒤 컨테이너를 자동 정리한다. 호스트 포트를 열지 않고 기존 DB를 사용하지 않는다.
기본 이미지는 `postgres:17-alpine`이며 실행 시 버전을 출력한다. 이번 실제 실행은 **PostgreSQL 17.11 / aarch64 / Alpine**이었다.
고객 1만 명과 주문 3만 개로 다음을 확인했다. 실행 시간과 계획은 환경·통계·캐시에 따라 달라질 수 있다.

| 확인 장면 | 실제 결과 |
|---|---|
| 주문 10개 JOIN, 기본 플래너 | Nested Loop; 고객 인덱스 `rows=1 loops=10` |
| 주문 3만 개 JOIN, 기본 플래너 | Hash Join; 고객 1만 행으로 해시 생성 |
| 다른 조인 방법을 실험 트랜잭션에서 억제 | Merge Join; 양쪽 인덱스로 정렬된 순서 읽기 |
| 같은 고객 4에 주문 두 개 | 두 주문을 포함해 결과 4행 |
| IN + 커버링 인덱스 + VACUUM | Index Only Scan; `Heap Fetches: 0` |
| 미정렬 VALUES 입력, 다른 조인 방법 억제 | 양쪽 입력에 Sort 후 Merge Join |

핵심 출력은 다음과 같다. 첫 계획의 SQL 요청은 한 번이다.

```text
Nested Loop (actual rows=10 loops=1)
  Index Scan using orders_pkey (actual rows=10 loops=1)
  Index Scan using customers_pkey (actual rows=1 loops=10)

Hash Join (actual rows=30000 loops=1)
  Seq Scan on orders (actual rows=30000 loops=1)
  Hash (actual rows=10000 loops=1)
    Buckets: 16384  Batches: 1  Memory Usage: 636kB

Merge Join (actual rows=4 loops=1)
  Sort
    Sort Key: 주문의 고객 ID
    Sort Method: quicksort  Memory: 25kB
    Values Scan
  Sort
    Sort Key: 고객 ID
    Sort Method: quicksort  Memory: 25kB
    Values Scan
```

마지막 계획은 실제 출력의 컬럼 표현을 읽기 쉽게 바꾼 것이다. DB가 양쪽 입력을 정렬하고 병합한다는 순서를 확인한다.

`loops`는 해당 실행 노드의 실행 횟수다. ID 비교 횟수나 SQL 요청 횟수가 아니다. 반복 실행 노드의 `actual rows`는 실행당 평균이므로 전체 출력량을 볼 때 `loops`도 함께 읽는다.
같은 고객 ID가 반복된다는 사실만으로 병합 조인의 `loops`가 줄어든다고 말할 수 없다. 반복 키의 재사용과 중첩 루프의 Memoize는 후속 학습 후보다.

- 관련: [[ds.complexity]] — 반복 탐색·해시 준비·정렬·출력량의 비용을 비교한다.
- 관련: [[db.normalization]] — 나뉜 주문·고객 정보를 연결하는 조회 비용과 데이터 중복의 선택이 맞닿는다.

## 확인 질문

- SQL 횟수는 51번에서 IN 일괄 조회로 2번이 된다고 직접 답했다.
- 적은 주문에는 기존 고객 인덱스를 사용하겠다고 선택하고 해시 생성 메모리와 탐색 복잡도를 근거로 들었다.
- 병합 조인을 투 포인터와 연결하고, 같은 고객의 다음 주문으로 이동해야 한다고 답했다.
- SQL 요청 수와 고객 인덱스의 `loops=10`을 구분했다. 중복 키가 있으면 병합 조인의 loops가 줄어든다는 해석은 교정했다.
- 정렬이 없으면 Nested Loop가 된다는 답, Hash Join을 GROUP BY/HAVING과 연결한 답, DB 내부 구현 여부의 혼란을 후속 설명으로 보완했다. 교정 후 독립적으로 재답변한 것으로 기록하지 않는다.
- 요청에 따라 시각화에 SQL 횟수와 loops, DB 내부 해시 생성, DB 정렬 후 투 포인터 이동을 모두 포함했다.
